## Stacked Todo

### 作りたいもの

通常のTodoに加え、1つのTodoの中へ複数の子Todoを含められる「Stacked Todo」を作る。作成時に、通常のTodoとStacked Todoのどちらにするかを選べるようにする。

たとえば「パスキーについて学ぶ」という親Todoの中へ、次の子Todoを持たせる。

- WebAuthnの登場人物を理解する
- 登録とログインの流れを図にする
- Cognitoでの対応方法を調べる
- 小さな試作を動かす

### 先に決めること

- 親Todoは、すべての子Todoが完了したら自動で完了にするか→yes
- 親Todoと子Todoのどちらに期限、優先度、タグ、学習ノートを持たせるか→両方
- 子Todoの並び替えと、別のStacked Todoへの移動を許可するか→yes
- 通常のTodoとStacked Todoを後から相互変換できるようにするか→yes
- 一覧画面で子Todoをどこまで展開し、詳細画面へ何を分けるか→通常は閉じていてトグルで開く
- 子Todoの入れ子を許可するか→これは現時点ではなし

暫定的には、入れ子は1段だけに制限し、親Todoには全体の目的、子Todoには実際の作業を持たせる

### データ構造の候補

| 案                                           | 更新のしやすさ     | 一覧取得                   | 将来の拡張                   | 現時点の見立て   |
| -------------------------------------------- | ------------------ | -------------------------- | ---------------------------- | ---------------- |
| 親Todoの中に子Todo配列を保存する             | 親全体の更新が必要 | 1件で取得できる            | 子Todoが増えると扱いにくい   | 小規模な試作向き |
| 子Todoを別レコードにし、`parentId`を持たせる | 子ごとに更新できる | 親子を組み立てる処理が必要 | 並び替えや移動を追加しやすい | 本実装の有力候補 |

本実装では、子Todoを独立したレコードとして扱う案が有力である。ただし、DynamoDBでの取得方法と並び順の保存方法を決めてから確定する。

approved

採用する。子Todoを独立レコードとして保存し、`parentId`と`position`を持たせる。既存データと通常Todoは`kind = standard`、親Todoは`kind = stacked`として扱う。個人用途で全件数が少ないため、一覧の`Scan`結果から親子を組み立て、子の構造変更時だけ兄弟を連番へ正規化する。詳細は[app.md](./app.md)に反映した。

### 具体例

1. 「パスキーについて学ぶ」へ、WebAuthnの理解、フローの図解、Cognitoの調査、試作を子Todoとして積む
2. 「Todoアプリをリリースする」へ、テスト、CDK synth、デプロイ、PC・スマホでの動作確認を積む

通常Todoは1回の完了操作で終わる作業、Stacked Todoは複数の独立した完了条件を持つ目的に使う。

### 完了と変換のルール

- 子Todoが1件以上あり、そのすべてが完了したときだけ親Todoを自動完了する
- 完了済みの子Todoを未完了へ戻す、または未完了の子Todoを追加・移動すると、親Todoも自動で未完了へ戻す
- 子Todoがある親Todoの完了状態は直接変更できない
- 通常TodoからStacked Todoへの変換では同じレコードを親にする
- Stacked Todoから通常Todoへの変換と親Todoの削除では、子Todoを削除せず独立した通常Todoへ戻す
- 子TodoをStacked Todoへ変換することはできず、入れ子は1段だけとする

### UIで検証したいこと

- 作成画面で「通常」と「Stacked」の違いが迷わず分かるか
- 親子のカードが重なって見づらくならないか
- スマホでも子Todoを追加、完了、並び替えできるか
- 通常TodoをStacked Todoへドラッグしたとき、移動先が明確に分かるか
- 親の進捗を件数やバーで見せる必要があるか
- 既存の優先度レーンへStacked Todoをどう置くか

- できればこのサイトに載っている、[gh-pr-grap](https://paper2.hatenablog.com/entry/2026/08/22/103649)みたいなUIにしたい

## ポモドーロと作業ログ

### 作りたいもの

Todoアプリへポモドーロタイマーを追加する。Todoの詳細（または一覧）からポモドーロを開始し、1本分の作業時間を計測する。1本が完了または中断するたびに、どのTodoに取り組んだかと合わせて作業ログとして記録する。記録した作業ログは、あとで振り返るだけでなく、MCP経由でAIからも取得できるようにする。

### 先に決めること

- ポモドーロの本数、作業時間、休憩時間を固定にするか、Todoごとに変更できるようにするか
- 作業中に別のTodoへ切り替えたとき、進行中のポモドーロをどう扱うか（中断として記録するか、破棄するか）
- 中断したポモドーロもログへ残すか、完了した本数だけを記録するか
- タイマーが動いている間にブラウザを閉じた、またはタブを切り替えた場合の扱い
- 複数デバイス（PC2台・スマホ）で同時にポモドーロを開始できてしまう状態を許すか

暫定的には、作業時間・休憩時間は固定値から始め、中断も含めてすべてログへ残す。振り返りだけでなくMCPからの取得でも「集中できなかった」という事実まで分かるようにするためである。

### 作業ログのデータ構造の候補

| 案                                                     | 更新のしやすさ                       | 一覧取得                                                 | 既存構成との親和性                        | 現時点の見立て   |
| ------------------------------------------------------ | ------------------------------------ | ---------------------------------------------------------- | ------------------------------------------- | ----------------- |
| 既存の`Todos`テーブルに`kind = pomodoroLog`のレコードとして保存する | Todoと同じAPI・認証をそのまま使える | 一覧`Scan`に混ざるため、Todo一覧側でのフィルタが必要      | 単一テーブルというMVPの方針に沿う          | 小規模な試作向き |
| 新しい`PomodoroLogs`テーブルを作る                     | 独立したCRUDが必要                   | Todo一覧の`Scan`を汚さない。`todoId`・日付での絞り込みを設計しやすい | テーブルが増え、CDKスタックの構成要素も増える | 本実装の有力候補 |

作業ログはTodo本体と更新頻度・参照のされ方が異なる（Todoは編集されるが、ログは基本的に追記のみ）ため、`PomodoroLogs`を別テーブルに分けたほうが素直だと考えている。ただし、DynamoDBの運用コストと個人用途での件数の少なさを踏まえると、単一テーブルに寄せる案も引き続き比較する。

### 記録する項目（案）

- 対象のTodo ID（`todoId`）
- 開始時刻・終了時刻（または開始時刻と実測の経過分数）
- 完了したか、中断したか（`completed` / `interrupted`）
- 何本目のポモドーロか（連続した作業のセット数）
- メモ（そのポモドーロで何をしたかの一言。任意）

### AIからの取得（MCP）

作業ログは、後述の「AIから更新するためのMCP」で計画している読み取り専用Toolの1つとして公開する予定である。最初は`list_work_logs`のような形で、期間やTodo単位で作業ログを取得できるところから試す。書き込み（ポモドーロの開始・記録）をMCP経由でAIに許可するかどうかは、Todo本体のMCP公開方針と合わせて別途判断する。

### UIで検証したいこと

- タイマーが動いている間、他の操作（Todoの編集・一覧の切り替え）を妨げないか
- 作業中のTodoが一覧のどこにいても、今どれに取り組んでいるかひと目で分かるか
- スマホでタイマーを開始し、画面を閉じてもポモドーロが継続していることをどう伝えるか
- 1日・1週間の作業ログをどう振り返り画面で見せるか（件数だけで十分か、Todoごとの内訳が要るか）

- [ ] 作業ログのデータ構造を`Todos`テーブル方式・別テーブル方式で比較し、どちらかに決める

## AIから更新するためのMCP

### 作りたいもの

このサイトにMCPサーバーを追加し、対応するAIからTodoの確認、作成、編集、完了ができるようにする。最初からすべての更新を許可せず、読み取り専用の接続から始め、認証と操作履歴を確認してから書き込みを開放する。

Cloudflare上でリモートMCPサーバーを構築しやすくする仕組みは候補として調査する。ただし、Cloudflareを採用すること自体はまだ決定しない。既存のAWS構成と認証をどこまで再利用できるかを比較して決める。

### 先に理解したいこと

- MCPにおけるHost、Client、Serverの役割
- Tool、Resource、Promptの違いと、Todo操作をどれで公開するか
- AIクライアントがMCPサーバーを見つけ、機能を呼び出すまでの流れ
- ローカル接続とリモート接続の違い
- リモートMCPでの認証、認可、アクセストークンの扱い
- MCPサーバーと既存REST APIの責務の分け方
- AIが外部入力を読んだときに起きるプロンプトインジェクションへの対策

実装時には、MCPの仕様とCloudflareの最新の公式資料を確認する。MCPサーバーからDynamoDBを直接操作するのではなく、既存のTodo APIを呼ぶ薄い変換層にする案を第一候補とする。これなら入力検証や更新ルールをWeb版と共有しやすい。

### 公開するToolの候補

| Tool            | 用途                             | 初期公開                     |
| --------------- | -------------------------------- | ---------------------------- |
| `list_todos`    | 条件に合うTodoを取得する         | 読み取り専用の試作で公開する |
| `get_todo`      | Todoの詳細と学習ノートを取得する | 読み取り専用の試作で公開する |
| `create_todo`   | Todoを作成する                   | 認証確認後に追加する         |
| `update_todo`   | 内容、優先度、タグなどを変更する | 認証確認後に追加する         |
| `complete_todo` | Todoを完了または未完了へ戻す     | 認証確認後に追加する         |
| `delete_todo`   | Todoを削除する                   | 初期段階では公開しない       |
| `list_work_logs` | ポモドーロの作業ログを期間・Todo単位で取得する | 読み取り専用の試作で公開する |

削除は取り返しがつきにくいため、MCP経由では当面公開しない。将来追加する場合も、完了済みTodoだけを対象にし、利用者の確認を必要とする。

### 設計上の論点

- Cognitoの利用者とMCPクライアントをどう結びつけるか
- 操作ごとの権限をどの単位で制限するか
- AIが行った更新を画面やログで識別できるようにするか
- 同じ操作が再送されたときの重複作成をどう防ぐか
- Cloudflare側に置く場合、AWS APIまでの認証情報をどう保管し、更新するか
- 将来、Kotlinアプリや別のAIクライアントからも同じMCPを使うか

## 認証セッションの自動更新

## パスキー認証

### 作りたいもの

現在のCognito認証にパスキーを追加し、対応端末ではパスワードを入力せずにログインできるようにする。認証は安全性への影響が大きいため、WebAuthnとパスキーの仕組みを理解し、別環境で登録とログインを試してから既存アプリへ組み込む。

最初はパスワード認証を廃止せず、パスキーを追加のログイン方法として提供する案を推奨する。端末の紛失やパスキーの同期失敗があっても、既存の方法で復旧できる状態を残すためである。

### 先に理解したいこと

- WebAuthnとパスキーの関係
- RP、ブラウザ、Authenticator、認証サーバーの役割
- 公開鍵を使う登録とログインの流れ
- RP ID、Origin、Challengeが何を守るのか
- 端末に限定される認証情報と、端末間で同期されるパスキーの違い
- フィッシング耐性が生まれる理由
- 端末を紛失した場合の復旧方法
- Cognitoと現在のフロント構成で利用できる方式と制約

Cognitoのパスキー対応状況や設定方法は変わる可能性があるため、実装時点の公式資料で確認する。

### 設計上の論点

- 既存ユーザーへパスキーを登録する導線
- パスキーを必須にするか、任意にするか
- 複数端末へ複数のパスキーを登録できるようにするか
- パスキーの名前、登録日時、最終利用日時を画面へ表示するか
- パスキーの削除時に再認証を求めるか
- すべてのパスキーを失った場合の復旧方法
- 現在の独自ログイン画面を維持するか、Cognito側の画面を利用するか
- LINE WebhookやMCPの認証と、利用者のパスキー認証をどこまで分離するか

## 着手順の暫定案

| 機能               | 最初の一歩                         | 本実装へ進む条件                                       |
| ------------------ | ---------------------------------- | ------------------------------------------------------ |
| Stacked Todo       | 利用例とUIの試作                   | 親子の完了ルールとデータ構造が決まっている             |
| ポモドーロと作業ログ | タイマーの基本フローとログ構造の比較 | 作業時間・休憩のルールと作業ログのデータ構造が決まっている |
| MCP                | ローカルで読み取り専用Toolを動かす | 認証、権限、操作履歴の方針が決まっている               |
| パスキー           | WebAuthnの独立した試作             | 復旧手段を含む認証フローを説明し、端末で検証できている |

アプリ機能として独立して試しやすいStacked Todoから設計を始める。ポモドーロと作業ログはタイマーのUIとログ構造の試作から進める。その後、MCPを読み取り専用で試し、更新権限は安全対策を確認しながら段階的に追加する。パスキーは認証全体へ影響するため、学習と別環境での検証を終えてから最後に本番へ組み込む。

## 実装前に判断すること

- Stacked Todoは1段の親子構造で十分か
- 作業ログを既存の`Todos`テーブルに混ぜるか、別テーブルに分けるか
- MCPサーバーをCloudflareとAWSのどちらへ置くか
- MCPの書き込み操作をどこまで許可するか
- パスキー導入後もパスワード認証を残すか
- 4機能のうち、次に実装へ進めるものはどれか

次に決めるべきなのは、Stacked Todoを使いたい具体的な場面を3件ほど出し、通常Todoとの違いを画面上でどう伝えるかである。MCPとパスキーは、先に小さな試作を作り、仕組みを自分の言葉で説明できる状態を着手条件とする。
